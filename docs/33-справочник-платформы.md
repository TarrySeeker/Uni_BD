## 1. Главная идея: headless

Платформа — это **бэкенд и админка отдельно, витрина отдельно**. Они общаются только
по HTTP через публичный `Storefront API` (`/api/storefront/v1/*`).

```
   Витрина магазина            Admik (этот репозиторий)
   ─────────────────           ────────────────────────
   каталог, корзина,   HTTP    админка + Storefront API
   оформление          ────▶   + БД + интеграции + CMS
   (что видит клиент)  ◀────   (что видит владелец)
```

Что это даёт: витрину можно переписать целиком, не трогая данные и админку; один и тот
же бэкенд обслуживает магазины любой ниши; владелец правит контент, не касаясь кода.

**Инвариант anti-tamper.** Витрина НИКОГДА не передаёт цены, итоги и веса — сервер
считает их сам и присланное игнорирует. Витрина передаёт только выбор: идентификаторы,
количества, промокод, адрес, способ доставки.

## 2. Четыре типа магазинов — определить ПЕРВЫМ делом

Тип определяет весь дальнейший план работ. Распознаётся автоматически:
`node scripts/adopt-storefront.mjs`.

### Тип Б1 — headless + витрина на фреймворке ⭐ основной

Витрина — отдельное приложение (Next.js и т.п.), отдельный контейнер, ходит только в API.

**Два адреса API — намеренно:**
```dotenv
ADMIK_API_URL="http://app:3000"                      # SSR внутри docker-сети
NEXT_PUBLIC_ADMIK_API_URL="https://admin.shop.example" # браузер (впекается в бандл)
```
Второй — build-arg: значение попадает в клиентский бандл на этапе сборки. **Смена
домена требует пересборки**, `up -d` её не подхватит.

**Когда:** по умолчанию. Нужен SEO, сложный UX, фильтры, личный кабинет.

### Тип Б2 — headless + статическая витрина

Чистый HTML + ванильный JS, отдаётся статическим сервером. Все запросы браузерные.

Адрес API впекается заменой плейсхолдера в конфиг-файле витрины при сборке образа.

**Когда:** готовый статический макет, простой каталог, SSR не нужен.
**Ограничение:** ключ API в статику положить нельзя (он был бы виден всем) → авторизация
только по Origin-allowlist.

### Тип А — монолит (витрина и админка в одном приложении)

Публичные страницы и `app/admin/*` в одном контейнере. **Для новых магазинов так не
делаем** — оставлено как исторический референс: именно оттуда взяты паттерны админки.

### Тип В — статический прототип без бэкенда

Просто макет. Этап согласования дизайна с владельцем, до подключения платформы. Это
не магазин, а вход в онбординг: из такого макета получается Б1 или Б2.

### Отдельно: способ деплоя (это не архитектура)

| Способ | Когда |
|---|---|
| **Docker Compose + Caddy** ⭐ | по умолчанию |
| **systemd без Docker** | на сервере нет Docker и поставить нельзя |

## 3. Вариации админок = модули

Админка одна и та же; разделы **включаются модулями** — это и есть «разные админки под
разные магазины» без правки кода.

```dotenv
ADMIK_MODULES="catalog,orders,cdek,cms,payments"
```
Плюс БД-override `shop_settings.module_overrides` (правка прямым SQL требует рестарта
`app` — см. §5).

Выключенный модуль убирает раздел из меню, закрывает его страницы гвардом и гасит
связанные проверки. Магазин-заявка без онлайн-оплаты и магазин без службы доставки —
**рабочие конфигурации, а не поломки**.

## 4. 🔴 Инстансы расходятся — главное предупреждение

Каждый развёрнутый магазин содержит **свою копию платформы**, и копии расходятся.
Это форки, а не одна кодовая база. Реальный замер трёх инстансов:

| | Инстанс А | Инстанс Б | Инстанс В |
|---|---|---|---|
| Миграций | **63** | 42 | 36 |
| Модулей | **8** | 5 | 5 |
| Роутов API | **37** | 34 | 19 |
| Тестов | **5408** | 2337 | 2185 |
| Мультиязычность | да | нет | нет |
| Мультивалюта | да | нет | нет |

**Одни и те же номера миграций заняты РАЗНЫМ содержимым.** В одном инстансе `0034` —
мультиязычность, в другом — внешние номера товаров, в третьем — цвета атрибутов.

### Что из этого следует

1. **Не переноси код между инстансами механически** — миграции конфликтуют по номерам.
   Перенос всегда сопровождается перенумерацией и ручным мержем правок существующих файлов.
2. **Перед сращиванием витрины сверяй контракт с кодом ТОГО САМОГО инстанса**, а не с
   документацией «вообще»:
   ```bash
   ls app/api/storefront/v1/     # какие эндпоинты реально есть
   cat lib/config/modules.ts     # какие модули знает эта копия
   ls db/migrations/ | tail -5   # на какой миграции остановились
   ```
3. **Обратный поток обязателен.** Именно расхождение — причина того, что уроки,
   оплаченные простоем боевого магазина, не доезжали до кита, и следующая сессия
   набивала ту же шишку. Правило возврата — в `CLAUDE.md`, уроки — в `docs/32`.

## 5. Кеш настроек: почему «сохранил, а не изменилось»

Эффективные настройки магазина кешируются в памяти процесса. Инвалидация происходит
автоматически при правке через UI и Server Actions.

**Правка `shop_settings` прямым SQL кеш НЕ инвалидирует** — до перезапуска `app` рантайм
отдаёт старый снимок. Ни `force-dynamic`, ни `no-store` тут не помогают: это не кеш
фреймворка. После прямого SQL — перезапуск приложения.

Исторически было хуже: состояние кеша жило в модульных переменных, и разные серверные
бандлы видели РАЗНЫЕ экземпляры модуля — правка через UI тоже не доезжала. Исправлено
переносом состояния на `globalThis` под registry-Symbol. Если похожий симптом появится
снова — искать модульное состояние, а не «кеш Next.js».

## 6. Безопасность: инварианты, нарушение которых уже стоило инцидентов

* **Server Action — это HTTP-эндпоинт.** «Из формы такое не придёт» защитой не является:
  валидирует схема, а не UI. Так прошёл stored XSS через поле, которое «не могло» прийти.
* **Rich-text из БД — только через санитайзер на сервере**, до отдачи витрине.
* **Секреты только из `.env`**, никогда в репозитории и никогда в коде витрины.
* **Публичная раздача — не свалка.** `COPY . .` в Dockerfile витрины однажды выложил в
  открытый доступ внутреннюю документацию с ТЗ заказчика.
* **Ответ об ошибке не должен работать оракулом.** «Кода нет» и «код не подходит» обязаны
  быть неразличимы, иначе перебор промокодов становится тривиальным.
* **Проверять И включённый модуль, И право.** Дашборд однажды показывал метрики
  сотруднику без единого права, потому что проверялся только модуль.
* **Сбой расчёта — это ошибка, а не ноль.** Расчёт доставки при сбое отдавал `0.00` с
  признаком «посчитано», и магазин возил бесплатно. Нужен явный отказ.

## 7. Порядок работ (кратко)

Полный ранбук — `docs/20`, оркестрируется скиллом `/onboard-shop`.

| Этап | Суть |
|---|---|
| **00** | Принять репозиторий владельца, распознать тип макета, привести к контракту compose |
| **0** | Преполёт: инструменты, зависимости, `.env` |
| **1** | Изучить фронтенд ПЕРВЫМ → «профиль магазина» |
| **2** | Интервью с владельцем (`docs/22`) — подтверждать найденное, а не спрашивать с нуля |
| **3** | Поднять БД: миграции + seed прав/ролей/владельца |
| **4** | Ретематизация: конфигурация и данные, БЕЗ правок кода платформы |
| **5** | Сращивание витрины с API (`docs/21`) |
| **6** | Две проверки: код-гейт + живой прогон в браузере |

**Каждый этап завершается чекпоинтом** — записью в `docs/00`/`docs/10` и списком «что
нужно от владельца». Владелец не программист, сессия может прерваться: процесс обязан
быть резюмируемым с любого места.

**Definition of Done:** БД готова · каталог и брендинг ретематизированы конфигурацией ·
витрина подключена к API · заведённое в админке доезжает до витрины · код-гейт зелёный ·
живой прогон пройден · раздел «Готовность магазина» без блокеров · всё задокументировано.
