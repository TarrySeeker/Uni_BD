# Уроки боевых магазинов: что ломается на самом деле

> **Читать ДО начала онбординга нового магазина** — сразу после `START-HERE.md` и
> `CLAUDE.md`, до `docs/20`. Этот документ не про архитектуру, а про то, обо что
> реально спотыкались предыдущие запуски. Каждый пункт оплачен простоем боевого
> магазина или потерянной сессией.
>
> Документ сводный и обезличенный: конкретные магазины не называются, ниши и домены
> опущены. Важен КЛАСС ошибки и признак, по которому её опознать.

---

## 0. Три вывода, которые история повторяет чаще всего

1. **Зелёный гейт ≠ работающий магазин.** Все по-настоящему дорогие находки —
   несбэкапленные медиафайлы, отсутствующий CSP, некупляемый товар с вариантами,
   `robots.txt`, отдающий HTML главной, — найдены ТОЛЬКО живой проверкой на реальных
   данных. Ни одна не была поймана тестами, хотя тестов было несколько тысяч и все
   зелёные. Отсюда правило платформы про ДВЕ проверки: код-гейт и живой прогон. Вторую
   нельзя пропускать «потому что первая зелёная» — они ловят разные классы.

2. **Разрыв «админка умеет — витрина не читает» — причина №1 жалоб владельцев.**
   Формулировка жалобы почти всегда одна: «меняю в админке, на сайте не меняется».
   В каждом новом проекте витрина пишется заново, поэтому класс воспроизводится
   снова и снова. Проверять сквозным путём: правка в админке → БД → Storefront API →
   страница витрины. Все четыре звена, а не «сохранилось же».

3. **Платформа опережает владельцев.** Механизмы (мультисклад, фото по цвету,
   автовыпуск сертификатов, зоны доставки) выкатывались и месяцами стояли ПУСТЫМИ:
   владельцы не вносят цены, фото и тексты и не дают ключи. Онбординг буксует не на
   коде. Поэтому список данных и доступов запрашивается В ПЕРВЫЙ ДЕНЬ (§4), а не
   тогда, когда всё готово и «осталось только наполнить».

## 1. Молчаливые блокеры конфигурации

Самый дорогой класс: инфраструктура жива, код исправен, тесты зелёные — а магазин не
работает. Система знает о проблеме, но нигде не говорит.

| Симптом у владельца | Настоящая причина | Как проверить сразу |
|---|---|---|
| «Доставка не считается, ПВЗ какие-то странные» | Ключи службы доставки пусты → модуль в режиме эмуляции, ПВЗ берутся из тестовых фикстур | Раздел **«Готовность магазина»** в админке; либо длина `CDEK_ACCOUNT`/`CDEK_SECRET` в `.env` |
| Статусы доставки не обновляются | `CDEK_CRON_SECRET` пуст → cron-роут отвечает 503. **Случалось в трёх магазинах подряд** | «Готовность»; `curl` cron-роута — должен быть не 503 |
| Вебхуки не приходят, хотя код приёма исправен | В кабинете службы доставки **нет ни одной подписки** — её никто не создавал | Кнопка «Проверить подписку на вебхуки» в разделе «Доставка» |
| «Оплата не работает» | Ключи терминала пусты → оплата эмулируется | «Готовность» |
| Письма не уходят | SMTP не настроен. Владельцы почти никогда не дают креды сразу | «Готовность» (когда почтовый модуль подключён к инстансу) |

**Правило.** Прежде чем чинить код интеграции — проверь, что ключи вообще доехали.
В одном из проектов владелец «передавал ключи трижды»; во ВСЕХ четырёх бэкапах `.env`
их длина была 0 — до сервера они не доехали ни разу. Затирания не было: ключи
отправлялись в переписку, но никто не прописывал их в `.env`.

**Не создавай незащищённый вебхук.** Если не заданы ни секрет, ни IP-whitelist, служба
доставки удалит подписку через сутки (эндпоинт отвечает 401), а владелец будет считать,
что всё настроено.

## 1-бис. Защиту чинят в одной функции, а трафик идёт через двойника

**Самый дорогой класс дефекта на этой кодовой базе.** Повторялся минимум четырежды,
и каждый раз выглядел как «мы же это починили».

Как устроен: признак или проверка вычисляются в двух местах независимо. Первое —
очевидное, его находят и защищают. Второе — то, через которое реально идёт боевой
путь. Точечный фикс не срабатывает вовсе, а тесты зелёные, потому что проверяют
починенную ветку.

Случаи:

| Двойники | Чем кончилось |
|---|---|
| Признак mock-оплаты считался и в конфиге, и в менеджере | Защита стояла в конфиге, боевой путь спрашивал менеджер — не срабатывала |
| Ограничитель частоты выбирался в двух функциях | Одна падала в память при недоступном хранилище молча |
| Извлечение IP: общая функция + по копии в каждом роуте вебхука | Копии разошлись: доверяли подделываемому заголовку и не проверяли формат |
| Проверка ссылки на безопасность — три реализации | Расползлись; закрытая дыра оставалась открытой в двух местах |

**Лечение, которое работает:** свести решение в ОДНУ функцию и добавить страж-тест,
который падает при появлении копии. Обычный юнит-тест здесь бесполезен — копия
проходит его так же, как оригинал. Пример: `tests/server/request-ip-single-source.test.ts`
проверяет не поведение, а что ни один роут не читает заголовки IP сам.

**Признак, по которому искать:** одна и та же формула («ключ пуст → значит demo»,
«взять первый сегмент заголовка») встречается в двух файлах.

## 1-тер. Fail-open: отсутствие настройки включает опасный режим

Родственный класс, но причина другая: не двойник, а **деградация по умолчанию в
сторону «работает»**, тогда как правильное поведение — «остановиться».

* **Оплата.** Пустые ключи терминала → эмуляция → фоновая доводка помечает заказ
  «оплачен». На боевом сервере это раздача товара бесплатно, без единого признака
  в интерфейсе. Сейчас в production такой запуск падает с внятной ошибкой, а
  честный демо-стенд обязан явно выставить `TBANK_ALLOW_MOCK=true`.
* **Расчёт доставки.** Сбой возвращал `0.00` с признаком «посчитано» — магазин
  возил бесплатно. Правильно — явный отказ, а не ноль.
* **Ограничитель частоты.** Недоступное хранилище → переход на память процесса
  молча: лимит перестаёт работать в кластере, но никто не узнаёт.

**Правило.** Для всего, что касается денег, доступа и лимитов, значение по умолчанию
при отсутствующей настройке — **отказ**, а не «как-нибудь продолжим». Демо-режим в
production включается только явным флагом, и его наличие видно в разделе
«Готовность магазина».

## 2. Правка не доезжает до витрины

**Кеш настроек.** Правка `shop_settings` **прямым SQL** не видна витрине, пока не
перезапущен `app`. Ни `force-dynamic`, ни `no-store` тут не помогают. Правки через
UI/Server Actions инвалидируют кеш сами — проблема только у прямого SQL.

Исторически было хуже: memo-кеш жил в модульных `let`, и Server Actions с Route
Handlers видели РАЗНЫЕ экземпляры модуля — правка через UI тоже не доезжала, до
рестарта. Исправлено переносом состояния на `globalThis` под registry-Symbol. Если
похожий симптом появится снова — искать модульное состояние, а не «кеш Next.js».

**Витрина игнорирует поля.** Классика: админка сохраняет, API отдаёт, витрина не читает.
В одном проекте таких полей нашлось около 25 (логотип, акцентный цвет, число знаков в
цене, шаблон title, соцсети, 5 из 7 типов CMS-секций давали пустое место). Проверять
сквозным путём, а не «сохранилось же».

**Zod-схема тихо отбрасывает поле.** Схема без нужного ключа не роняет запрос — она
молча выкидывает значение. Симптом: «сохранил адрес, а его нет».

**Один плохой ключ роняет всю секцию.** Если валидировать секцию настроек целиком, одно
некорректное поле откатывает НА ДЕФОЛТЫ весь ключ, а не только себя. Владелец видит,
что «слетело всё».

## 3. Формы, которые молча теряют данные

* **Фильтр неполных строк в репитере.** Форма отбрасывала строки без всех обязательных
  полей и рапортовала «сохранено» — запись просто исчезала после перезагрузки. Фильтр
  нужен (иначе сервер вернёт отказ), но он обязан быть **громким**: остановить
  сохранение и показать, какие строки заполнены частично. Ввод не терять.
* **Снятие галочки/значения теряется**, если форма отправляет только «изменённые»
  элементы, а снятие не считает изменением.
* **`error.flatten()` схлопывает вложенные пути** — ошибка валидации не подсвечивает
  виновное поле, владелец видит «что-то не так» без указания где.
* **Ошибки Zod на английском** уезжают покупателю и в русскую админку. Есть
  `lib/zod-locale.ts` — использовать.
* **Два расходящихся набора дефолтов** для одного ключа (один в форме, другой в рантайме)
  → форма показывает одно, работает другое. Особенно опасно, когда касается денег.

## 4. Что запросить у владельца В ПЕРВЫЙ ДЕНЬ

Онбординг буксует не на коде — на данных. Этот список отдаётся владельцу сразу,
одним сообщением, и по нему ведётся учёт.

**Доступы и ключи** (без них модуль работает в эмуляции, а не «почти работает»):
1. Ключи службы доставки (договорные, боевые) — и подтвердить, что они **прописаны в
   `.env` на сервере**, а не «отправлены в переписке».
2. Ключи платёжного терминала — либо явное решение «онлайн-оплаты не будет»
   (тогда модуль выключается, и это нормальная конфигурация).
3. SMTP-креды — иначе не будет ни писем о заказе, ни восстановления пароля.
4. Домен + доступ к DNS.

**Данные каталога** (самый частый тормоз):
5. Цены. В одном проекте цена стояла у 2 позиций из 4484 — продавать было физически
   нечего. Проверять не «есть ли выгрузка», а сколько позиций реально с ценой.
6. Фотографии. Бывает, что их нет ни в учётной системе, ни у поставщика по API.
   Выяснять ЗАРАНЕЕ, а не после написания импорта.
7. Тексты: «О компании», описания. Пустой черновик и `Lorem ipsum` в карточке дорогого
   товара видит покупатель.
8. Реквизиты юрлица — иначе строка в подвале просто не выводится.

**Организационное:**
9. **Пароль от админки владелец должен где-то сохранить.** Реальный тупик: владелец
   забыл пароль, ссылки «забыли пароль» нет, SMTP пуст — попасть в собственную админку
   невозможно. Аварийный выход — `scripts/reset-owner-password.mjs` на сервере.
10. Кто перезапускает сервисы, если у агента нет прав на `systemctl`/`docker`.

## 5. Готчи выката

* **`NEXT_PUBLIC_*` вшивается в клиентский бандл на этапе сборки.** Смена домена
  требует ПЕРЕСБОРКИ; `up -d` её не подхватит.
* **`docker load` перетирает тег `:current`** — тег `:rollback` ставить ДО загрузки,
  иначе «откат» вернёт образ недельной давности.
* **Конфиг Caddy монтируется по inode** — `cp`/`tar` поверх файла контейнер не увидит,
  нужен `--force-recreate`.
* **Нельзя поднимать `next start` посреди сборки.** Один чанк навсегда отдаёт 404, при
  этом файл ЛЕЖИТ на диске: витрина не гидрируется, корзина и фильтры мертвы. Лечится
  рестартом сервиса, диагностируется мучительно.
* **Сверять весь md5-слепок дерева, а не дельту волны.** Стенд однажды отстал от
  репозитория на 120 файлов именно из-за точечных выкаток.
* **`rsync` всегда с `--exclude '.env*' --exclude backups`** — иначе снесёт боевой `.env`.
* **Бэкап, который рапортует успех, может ничего не копировать.** Медиафайлы (819 МБ)
  не бэкапились 13 дней, и 15 прогонов подряд писали «готово»: утилита отсутствовала,
  а скрипт считал это нормой и выходил с кодом 0. Проверять бэкап по РАЗМЕРУ и
  восстановлением, а не по коду возврата.
* **Бэкап на том же сервере — не бэкап.** Нужна копия вне машины.

## 6. Готчи проверки в браузере

* **Сетевые отказы в песочнице агента — чаще всего среда, а не дефект прода.** Холодный
  коннект может висеть 20–25 секунд и давать ложное «раздел недоступен». Любой
  браузерный отказ перепроверять `curl` с самого сервера и логами прокси.
* **Проверяй сначала свой тест, потом обвиняй прод.** В одном живом прогоне 4 из 5
  «найденных багов» оказались ошибками самих тестов: клик мимо элемента, неверный
  селектор, не та кнопка. Настоящий баг был один.
* **TLS диагностировать только с самого сервера** — снаружи из песочницы 443 может
  выглядеть сломанным, хотя изнутри всё исправно.

## 7. Разрушительные операции

* **Удаление категории с товарами** однажды прошло молча на боевых данных — раздел
  исчез у покупателей. Проверять связи и предупреждать явно.
* **Удаление последнего варианта** делало товар некупляемым. Учитывать, что у
  большинства товаров вариант ровно один.
* Внешние ключи с `ON DELETE CASCADE` превращают «удалю одну строчку» в цепную реакцию.
  Перед удалением — смотреть, что утянется следом.

## 8. Безопасность: что уже стреляло

* **Stored XSS через поле, которое «из формы не придёт».** Server Action — это HTTP-эндпоинт;
  валидировать надо схемой, а не рассчитывать на UI. Копируя механику из образца,
  сверять и его ВХОДНУЮ схему, а не только обработчик.
* **CSP отсутствовал вовсе** — второго рубежа против XSS не было.
* **Дашборд показывал метрики сотруднику без единого права.** Проверять И включённый
  модуль, И право.
* **Публичная выдача не должна отдавать служебные файлы.** `COPY . .` в Dockerfile
  выложил в открытый доступ внутреннюю документацию с ТЗ заказчика.
* **Rich-text из БД — только через санитайзер на сервере**, до отдачи витрине.
* **Не всякий заголовок с IP можно использовать как IP.** Левый сегмент
  `X-Forwarded-For` подконтролен клиенту: прокси лишь дописывает свой адрес
  справа, присланное сохраняет. Доверять надо `X-Real-IP`, который наш прокси
  ПЕРЕЗАПИСЫВАЕТ адресом реального соединения. Пока приоритет был обратным,
  ротацией одного заголовка обходилась защита от перебора паролей (каждый запрос —
  «новый клиент», свежий лимит), проходился IP-фильтр вебхуков и отравлялся журнал
  аудита чужими адресами.
  ⚠️ **Порядок выкатки строгий: сначала конфиг прокси, потом код.** Обратный
  порядок открывает окно, где код уже доверяет заголовку, а прокси его ещё не
  перезаписывает — это хуже, чем было. Обратная последовательность (конфиг раньше
  кода) безопасна: пока код не обновлён, перезапись ни на что не влияет.
  ⚠️ Перед нашим прокси **не должно быть CDN или L4-балансировщика**: тогда
  «реальный адрес соединения» окажется адресом CDN, все посетители схлопнутся в
  один ключ лимита, и магазин положит сам себя.

## 8-bis. Согласия покупателя: 152-ФЗ ломает «одну галочку» (урок живого магазина)

**Что нашли на бою.** В чекауте стояла ОДНА галочка «Мне есть 18 лет, и я соглашаюсь
с политикой обработки персональных данных», а форма обратной связи собирала имя и
контакт **вообще без согласия**. И то, и другое — нарушение.

**Правило (ч.1 ст.9 152-ФЗ в ред. ФЗ-156 от 24.06.2025, действует с 01.09.2025):**
согласие на обработку ПДн оформляется **отдельно от иных информации и документов**.
В веб-интерфейсе это означает отдельный визуальный элемент: галочка «ПДн» не может
быть склеена с акцептом оферты, подтверждением 18+ или чем-либо ещё. Отсюда минимум
**три обязательные раздельные галочки** (ПДн / оферта / возраст, если он нужен ниши)
и **четвёртая необязательная** — рекламная рассылка. Штраф ст.13.11 ч.1 КоАП — до
700 тыс. ₽.

**Смежные правила, о которые спотыкаются:**
- галочки **пустые по умолчанию** — предустановленная отметка запрещена ст.16 ЗоЗПП
  (до 500 тыс. ₽);
- отказ от **маркетингового** согласия НЕ должен мешать покупке (ст.16 ЗоЗПП + ст.18
  ФЗ-38, презумпция вины продавца, до 1 млн ₽ — самый дорогой «сайтовый» состав);
- любая форма, собирающая имя/телефон/почту (обратная связь, подписка, «перезвоните
  мне»), — это сбор ПДн, ей нужно своё основание. Проверять НЕ только чекаут.

**Механизм в ките (`lib/consent/`, миграция `0037_consent_log.sql`):**
1. **Согласие проверяет СЕРВЕР.** Галочка в браузере обходится прямым запросом к API —
   это тот же класс дефекта, что stored XSS из §? («из формы не придёт» ≠ защита).
   Схема витрины требует `z.literal(true)` на каждое обязательное согласие.
2. **Согласие ПИШЕТСЯ в журнал.** По закону наличие согласия доказывает **оператор**,
   а отрисованная галочка не доказывает ничего: её нет ни в БД, ни в логах. В
   `consent_log` пишется строка на КАЖДЫЙ вид согласия + **текст формулировки и её
   версия** (согласие оценивается по редакции, действовавшей на момент дачи) + IP и
   User-Agent. Таблица **append-only**: в GRANT намеренно нет UPDATE/DELETE.
3. **Текст берётся с сервера** (`CONSENT_TEXTS`, отдаётся витрине в `/settings`), а не
   из копии в вёрстке. Иначе в журнал попадёт один текст, а покупатель увидит другой,
   и доказательная ценность журнала обнулится.
4. **Сбой журнала не роняет заказ** (`recordConsentSafe`): покупатель согласие дал,
   отказывать ему из-за недоступности журнала несправедливо — но и терять факт молча
   нельзя, поэтому ошибка уходит в лог.

**Три готчи реализации:**
- ⚠️ **Не клади `consent` в общий shape заказа.** По нему же строится
  `ManualOrderSchema` — заказ, который менеджер заводит в админке со слов покупателя
  по телефону. Там галочек нет и быть не может. Согласие — свойство **канала**
  (витрина), а не заказа: `CreateOrderSchema = shape + consent`, а репозиторий
  типизируется `ManualOrderInput` (он согласий не пишет вовсе).
- ⚠️ **Идемпотентный повтор заказа согласие НЕ пишет.** Иначе ретраи сети и двойные
  клики набивают журнал дублями.
- ⚠️ **Тесты витрины: кастомный чекбокс скрыт** (`.consent input { display:none }`),
  Playwright его не кликнет — кликать надо видимый `.box`. Клик по `label` промахнётся
  в ссылку, если в подписи их две («оферта» + «порядок возврата»).

**Тексты документов** (Политика ПДн под ст.18.1, «Возврат» под ст.26.1, оферта) —
ниша-независимые по структуре, но пишутся под КОНКРЕТНУЮ модель продаж. Спрашивать у
владельца до написания: (1) продажа с оплатой на сайте или заявка с оплатой вне сайта;
(2) товар готовых размеров или индивидуальный пошив — от этого зависит, законен ли
отказ в возврате (при готовых размерах «возврату не подлежит» **незаконно**, срок 7
дней, а без письменной памятки в посылке — 3 месяца).

## 8-тер. Унаследованная тема прячет ВСЕ нативные поля — покупка невозможна

**Стоимость урока: боевой магазин 4 дня не принимал заказы вообще.** Ни одного заказа
с момента переключения домена, при живом трафике. Владелец описал это как три разные
жалобы: «не проходит оплата», «не создаётся заказ», «нельзя поставить галочки».
Причина у всех трёх одна.

**Класс.** Когда витрина строится поверх ДИЗАЙНА СТАРОГО САЙТА (скопированный
`app.css` / тема прошлой CMS), в теме почти всегда есть приём «спрятать нативный
контрол и нарисовать свой»:

```css
input[type=checkbox]:checked, input[type=checkbox]:not(:checked),
input[type=radio]:checked,    input[type=radio]:not(:checked)
{ position: absolute; left: -9999px; }
```

Он корректен ровно до тех пор, пока у КАЖДОГО поля есть свой оформленный
`<label for=...>` с псевдоэлементом. Новые поля платформы (согласия 152-ФЗ, выбор
способа доставки) такой пары не имеют — и физически уезжают за край экрана. Поле
`visible`, `enabled`, событие `change` работает, но кликнуть по нему НЕЧЕМ.

**Что было сломано одновременно:** обе галочки согласия (→ кнопка «Оплатить» вечно
`disabled`), все три радио выбора доставки, галочка подписки в подвале, галочка формы
обратной связи. Каждая из них по отдельности блокирует свою форму целиком.

**Как опознать (30 секунд).** В браузере на боевом домене:

```js
[...document.querySelectorAll('input[type=checkbox],input[type=radio]')]
  .map(el => ({ cls: el.closest('label')?.className, x: el.getBoundingClientRect().x }))
  .filter(o => o.x < 0)          // непусто → поля за экраном
```

**Лечение.** НЕ править чужую тему (её правило нужно остальным формам сайта), а
перекрыть точечно в `storefront.css` — он подключается ПОСЛЕ темы, селектор
специфичнее:

```css
.sf-checkout__consent input[type='checkbox'],
.sf-checkout__consent input[type='checkbox']:checked,
.sf-checkout__consent input[type='checkbox']:not(:checked) {
  position: static; left: auto; appearance: auto; -webkit-appearance: checkbox;
}
```

Псевдоклассы `:checked` / `:not(:checked)` в селекторе ОБЯЗАТЕЛЬНЫ — именно в такой
форме записано правило темы, без них специфичности не хватит.

**Готчи диагностики (стоили половины сессии):**

- 🔴 **`curl` по странице оформления ВСЕГДА показывает лоадер и ноль галочек** — это
  НОРМА, а не баг: форма рендерится только после гидрации (`if (!mounted)`), корзина
  живёт в `localStorage`. Текстовыми детекторами чекаут диагностировать БЕСПОЛЕЗНО.
- 🔴 **jsdom не заменяет браузер**: Turbopack-бандл падает с `chunk path empty but not
  in a worker`. Приём «прогнать js в `node:vm`» здесь не работает.
- ✅ **Браузер поднимается прямо в песочнице**: `sudo npx playwright install-deps
  chromium` (sudo есть), путь к бинарнику задавать ЯВНО. Наружу 443 режется →
  `ssh -N -L 8443:127.0.0.1:443 <сервер>` + `--host-resolver-rules=MAP <домен>
  127.0.0.1:8443`. Туннелю нужен правильный SNI (`--resolve домен:8443:127.0.0.1`),
  иначе TLS alert. Крупный файл через туннель может висеть — проверять `curl` с сервера.
- 🔴 **Сначала доказать, что БЭКЕНД жив**, и только потом копать витрину: полный путь
  `POST /api/storefront/v1/orders` + `/payments/init` проверяется `curl` с сервера за
  минуту. В этом инциденте API был ИСПРАВЕН всё время (тот же вывод, что в §2).

## 8-кватер. Печать накладной СДЭК: URL лежит внутри `entity`

**Класс: зелёный тест маскировал боевой баг, потому что мокал выдуманный формат ответа.**

Печать в СДЭК двухшаговая: `POST /v2/print/orders` → задача, затем
`GET /v2/print/orders/{uuid}` → ссылка на PDF. Реальный ответ второго шага:

```json
{ "entity": { "uuid": "...", "url": "https://api.cdek.ru/v2/print/orders/<uuid>.pdf",
              "statuses": [{ "code": "READY", "name": "Сформирован" }] },
  "requests": [{ "state": "SUCCESSFUL" }] }
```

Ссылка — **внутри `entity`**. Код читал `raw.url` (поле верхнего уровня, которого в
ответе нет) → опрос всегда возвращал `null` → печать ВСЕГДА падала с «PDF ещё не
готов», даже когда СДЭК уже отдал `READY`. Оператор не мог распечатать ни одной
накладной. Тест при этом был зелёный — он мокал ответ как `{ url }`, то есть
проверял формат, которого не существует.

**Второй слой той же проблемы.** Даже с правильной ссылкой открыть её в новой вкладке
нельзя: PDF требует `Authorization: Bearer <token>` (без токена → 401, с токеном →
`application/pdf`). Прямая ссылка из `cdek_shipments.print_url` в браузере всегда даст
пустую страницу. Нужен прокси-роут админки, который сам сходит в СДЭК с токеном:
`GET /api/cdek/label/<orderId>?kind=waybill|barcode` под правом `cdek.manage`
(накладная содержит ПДн получателя — в открытый доступ отдавать нельзя).

**Правило, которое отсюда следует:** мок ответа внешнего API пишется по РЕАЛЬНОМУ
ответу, снятому живым вызовом, а не по тому, как API «должен» отвечать. Иначе тест
проверяет фантазию автора. Признак болезни в тесте — литерал вида `{ url: '...' }`,
не совпадающий ни с одним примером из документации провайдера.

## 9. Как пользоваться этим документом

1. Перед онбордингом — прочитать целиком (10 минут).
2. §4 отдать владельцу **в первый день**, не откладывая.
3. После запуска — пройти разделом **«Готовность магазина»** в админке: он машинно
   проверяет большинство пунктов §1.
4. Найдя НОВЫЙ класс ошибки — дописать сюда. Смысл документа в том, чтобы следующая
   сессия начинала с накопленного опыта, а не с нуля. Уроки, оставшиеся в конкретном
   магазине, для платформы не существуют.
