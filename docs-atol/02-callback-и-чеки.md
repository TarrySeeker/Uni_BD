# АТОЛ Pay — Callback и фискализация

## Куда приходит

Один URL на все события. Приоритет:
1. `additionalProps.notificationUrl` в методе регистрации платежа (наш случай);
2. настройка ЛК: **Настройки → Настройки заказов → Настройки колбэков**.

Тип события различается по полю `type` в теле запроса.

## 🔴 ПОДПИСИ У CALLBACK НЕТ

В документе нет ни HMAC, ни секрета уведомлений, ни контрольной суммы —
ни в таблице 6 (`payment`/`deposit`/`cancel`/`refund`), ни в таблице 7 (`fiscal`).

Это ОТЛИЧИЕ ОТ Т-БАНКА И ОЗОНА, где вебхук проверяется подписью
(`lib/payments/ozon/sign.ts: notificationSign`).

**Следствие: тело callback само по себе НЕ доказывает, что его прислал АТОЛ.**
Если доверять ему как есть, кто угодно, узнав URL вебхука, сможет объявить
неоплаченный заказ оплаченным.

Защита, которую поэтому ОБЯЗАНЫ построить сами (иначе оплата — дыра):
1. **Секрет в query-параметре `notificationUrl`.** Документ прямо разрешает
   произвольные query-параметры. Кладём туда длинный случайный токен и
   сверяем его на входе за постоянное время. Секрет в URL — не идеал
   (попадает в логи), но это единственный канал аутентификации, который даёт API.
2. 🔴 **Обязательная сверка через `GET /payments/{orderId}/status`.** Callback
   считаем лишь СИГНАЛОМ «сходи проверь», а решение о смене статуса заказа
   принимаем ТОЛЬКО по ответу API, запрошенному нами по токену. Это
   единственная по-настоящему надёжная проверка, и она не зависит от секрета в URL.
3. **Сверка суммы** заказа с `amount` из ответа API перед пометкой «оплачен».
4. Идемпотентность по `orderId` + тип события: callback может прийти повторно.

## Таблица 6 — `payment` / `deposit` / `cancel` / `refund`

| Поле | Обяз. | Формат | Значения |
|---|---|---|---|
| `status` | Да | string | `success` \| `fail` \| `error` |
| `orderId` | Да | string | идентификатор заказа |
| `type` | Да | string | `payment` \| `deposit` \| `cancel` \| `refund` |
| `paymentStatus` | Да | number | числовой статус (таблица статусов в 01) |
| `sessionType` | Да | string | `oneStep` \| `twoStep` |
| `amount` | — | number | сумма в копейках |
| `paidAt` | Нет | string | время оплаты |
| `canceledAt` | Нет | string | время отмены/возврата |
| `depositedAt` | Нет | string | время второй стадии |
| `errorMessage` / `errorCode` | Нет | string | при ошибке |

Пример успеха:
```json
{ "status": "success", "orderId": "fcae8e64-...", "amount": 10000,
  "type": "payment", "paymentStatus": 0, "sessionType": "oneStep",
  "paidAt": "2024-05-04T13:21:00+03:00", "canceledAt": null }
```

⚠️ В примере документа `"status": "success"` соседствует с `"paymentStatus": 0`
(= «в обработке»). То есть `status` — это статус ОБРАБОТКИ ЗАПРОСА, а НЕ факт
оплаты. **Оплату определять только по `paymentStatus`, подтверждённому сверкой.**

## Таблица 7 — `fiscal`

| Поле | Обяз. | Значения |
|---|---|---|
| `status` | Да | `success` \| `fail` |
| `orderId` | Да | — |
| `type` | Да | `fiscal` |
| `receiptId` | Да | идентификатор чека |
| `amount` | Да | number |
| `receiptType` | Да | `sell` (приход) \| `sell_refund` (возврат прихода) |

## 🔴 Чек может не пробиться, а деньги спишутся

Дословно из документа: «**транзакция не отменяется, если чек отправился
неуспешно**».

То есть возможна ситуация: деньги у покупателя списаны, чека нет — нарушение
54-ФЗ, которое мы заметим только по жалобе. Поэтому `fiscal` со `status: fail`
обязан писаться в журнал и поднимать заметный алерт оператору, а не молча
проглатываться.

## Блок `receipt` при регистрации платежа

- `providerId: 100` — АТОЛ Онлайн (фискализация на стороне АТОЛа, отдельная
  интеграция с кассой НЕ нужна)
- `sno` — система налогообложения
- `positions[]`: `name`, `price` (копейки), `quantity` (тысячные), `measure`,
  `paymentMethod`, `paymentSubject`, `tax`, опц. `isAgent`/`agentId`/`supplierId`
- `buyer.email` — подставляется на форме оплаты

`paymentSubject` (признак предмета расчёта), выдержка:
`0` Товар, `1` Подакцизный товар, `2` Работа, `3` Услуга, `4` Ставка азартной игры,
`9` Платеж, `10` Агентское вознаграждение, `12` Иной предмет расчёта,
`17` Туристический налог, `26` Выдача денежных средств.
Полный список — `GET /v1/ecom/receipts/dictionaries`.

🔴 `INVALID_RECEIPT_AMOUNT` — сумма платежа должна сходиться с суммой позиций
до копейки. Доставка и скидки обязаны быть отдельными позициями, иначе отказ.

## Настройка в ЛК (инструкция заказчика)

Касса — **АТОЛ Онлайн** (`online.atol.ru/lk`): «Мои компании» →
«Настройки интегратора» → скачать файл.

АТОЛ Pay (`lk.atolpay.ru`):
- Настройки → Настройки заказов → вкладка **«Провайдер чеков»** → загрузить
  файл, **ФФД 1.05** → сохранить.
- Вкладка **«Оплата»**: банк для карт — Т-Банк; СБП — Сбербанк; T-Pay — вкл.;
  название магазина (на платёжной форме); обратный URL.
- Агенты и поставщики (если нужны по 54-ФЗ): Настройки → Настройки заказов →
  «Агент» / «Поставщики» (оттуда берутся `agentId` / `supplierId`).
