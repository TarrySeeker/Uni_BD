# Почтовый модуль (`lib/mail`)

**Статус:** реализован. Миграция `0061_mail_log`.

---

## 1. Зачем он появился

До этой волны **в платформе не было e-mail вообще**: `grep` по `lib/` не находил ни
`nodemailer`, ни SMTP, ни каталога `mail/`. Последствия, признанные критичными:

1. **Главное — деньги.** Покупатель, купивший подарочный сертификат, получал код
   **только на странице успеха оплаты**. Закрыл вкладку, потерял ссылку, сменил
   устройство — и деньги на предъявителя исчезли вместе с вкладкой. Восстановить их
   владелец не мог: код не отправлялся никуда и нигде не фиксировался факт выдачи.
2. Заказ не подтверждался письмом — покупателю нечего было предъявить.
3. Смена статуса доставки не доходила до покупателя, **хотя карта шаблонов уже
   существовала**: `STATUS_TO_CLIENT_TEMPLATE` в `lib/cdek/services/status-map.ts`
   была написана при портировании модуля СДЭК и не вызывалась НИКЕМ — `grep` давал
   только объявление и тест. Мёртвый код.

Модуль закрывает всё три пункта и **переиспользует** существующую карту вместо того,
чтобы заводить рядом второй словарь.

## 2. Архитектура

```
lib/mail/
  types.ts          — типы и порты (MailTransport, MailJournal). Без зависимостей.
  config.ts         — резолв SMTP-конфигурации из env. НЕ бросает никогда.
  templates.ts      — рендер письма (HTML + текст) на ru/en/fr. Чистый модуль.
  transport.ts      — единственное место, знающее про nodemailer и сеть.
  repository.ts     — журнал отправок (таблица mail_log).
  sender.ts         — отправка: транспорт + журнал + ретраи. НЕ бросает.
  notifications.ts  — точки вызова: «заказ оплачен», «сменился статус доставки».
  order-snapshot.ts — чтение заказа/сертификатов/ссылки для писем.
  resend.ts         — пересборка и повторная отправка по записи журнала.
  cron.ts           — воркер досылки под advisory-lock.
  actions.ts        — Server Action «отправить повторно» (defineAction).

app/api/cron/mail/[task]/route.ts   — крон-роут (задача retry-failed).
app/admin/(panel)/mail/             — раздел админки «Письма».
db/migrations/0061_mail_log.sql     — журнал отправок.
```

**Слои разделены так, что сеть трогает ровно один файл** (`transport.ts`). Всё
остальное тестируется без SMTP и без БД через инъекцию портов (ADR-004).

### Ключевые инварианты

| Инвариант | Где обеспечен | Почему |
|---|---|---|
| `sendMail` **не бросает никогда** | `sender.ts` | Вызывается после фиксации оплаты. Throw откатил бы факт оплаты (тот же прецедент, что в `gift-certificates/auto-issue.ts`) |
| Не настроенная почта = рабочее состояние | `config.ts`, `sender.ts` | Магазин без SMTP обязан продавать. Мультитенантность |
| Код сертификата **не попадает** в журнал и логи | `types.ts`, `repository.ts`, миграция | Деньги на предъявителя; логи уезжают в docker json-file и в бэкапы |
| Пользовательские данные экранируются | `templates.ts` (`escapeHtml`) | HTML рендерит чужой почтовый клиент → XSS |
| Язык — **покупателя**, не оператора | `notifications.ts` | `customers.preferred_locale` → язык магазина. `users.ui_locale` не используется |

## 3. Хранение SMTP-секретов: только `.env`

**Решение: секреты живут исключительно в `.env` инстанса. Админка их не хранит, не
показывает и не редактирует.**

Обоснование:

* **Область поражения.** Пароль SMTP — полный доступ к отправке от имени магазина:
  им рассылают фишинг с домена владельца, и он часто совпадает с паролем ящика.
* **Кто увидел бы.** В `shop_settings` он стал бы доступен каждому оператору с правом
  `settings.manage` — а раздел настроек в Admik один на всё.
* **Размножение секрета.** Дампы БД ежесуточно уезжают в бэкап-контейнер и оффсайт
  (`docker-compose`, сервис `backup`). Секрет в БД = секрет в каждом бэкапе.
* **Прецедент платформы.** Ключи эквайеров (`TBANK_*`, `PAYKEEPER_*`, `ALFABANK_*`),
  СДЭК (`CDEK_*`) и S3 (`S3_*`) уже живут в `.env` ровно по этим причинам. Почта не
  заслуживает исключения.

Раздел админки «Письма» показывает **состояние**: «настроено / не настроено» и адрес
отправителя. Этого достаточно, чтобы владелец понял, почему письма в статусе
«Пропущено», и при этом не увидел пароля.

Настраиваемое **без секретов** (название магазина в подписи письма) берётся из
настроек магазина — мультитенантно, без хардкода.

## 4. Переменные окружения

| Переменная | Обязательна | По умолчанию | Смысл |
|---|---|---|---|
| `SMTP_HOST` | да, для включения | — | Адрес релея. **Пусто → почта выключена** |
| `SMTP_PORT` | нет | `587` | 587 = STARTTLS, 465 = неявный TLS |
| `SMTP_USER` | нет | — | Логин. Пусто допустимо (релей без аутентификации) |
| `SMTP_PASSWORD` | нет | — | Пароль. Для Яндекс/Gmail/Mail.ru — **пароль приложения** |
| `SMTP_SECURE` | нет | `false` | `true` = неявный TLS. Порт 465 сам по себе secure не включает |
| `MAIL_FROM` | **да** | — | Адрес отправителя. Без него почта остаётся выключенной |
| `MAIL_FROM_NAME` | нет | — | Отображаемое имя (название магазина) |
| `MAIL_TIMEOUT_MS` | нет | `15000` | Таймаут соединения/отправки |

Крон-задача досылки своего секрета не требует — используется общий
`CDEK_CRON_SECRET`, как у остальных `/api/cron/*`.

**Минимальный рабочий набор:** `SMTP_HOST` + `MAIL_FROM` (+ обычно `SMTP_USER`,
`SMTP_PASSWORD`, `MAIL_FROM_NAME`).

## 5. Точки вызова

| Событие | Файл | Порядок |
|---|---|---|
| Оплата подтверждена (T-Банк / PayKeeper / Альфа-Банк) | `lib/payments/*/service.ts`, хук `autoIssueGiftsAfterCommit` | **После коммита** оплаты и **после** автовыпуска сертификатов — иначе кода ещё нет в БД |
| Смена статуса доставки | `lib/cdek/services/webhook.ts` | **После** `advanceDeliveryStatus`, **до** `markStatusLogProcessed` — чтобы ретрай вебхука догнал неотправленное письмо |
| Досылка неотправленного | `app/api/cron/mail/retry-failed` | Каждые 20 минут |
| Ручная пересылка | Админка → «Письма» → «Отправить повторно» | Право `orders.write`, пишется в аудит |

Во всех точках сбой почты **не влияет** на денежный путь: он становится
`failed`-записью журнала, которую подхватывает крон.

## 6. Журнал отправок (`mail_log`)

Хранит **метаданные**: адресат, тип письма, язык, статус, попытки, ошибка, тема,
ссылка на заказ, времена.

**Не хранит** тела письма и кода сертификата. Причина: хранение означало бы держать
деньги на предъявителя вторым экземпляром в таблице, доступной любому оператору
раздела, и тащить их во все дампы БД. При досылке письмо **рендерится заново из
заказа** — побочно это ещё и защита: отключённый или истёкший код повторное письмо
уже не назовёт.

Статусы: `pending` → `sent` | `failed` | `skipped`.
`skipped` — отправки не было **осознанно** (почта не настроена, у заказа нет адреса).
Крон её не ретраит: иначе магазин без SMTP вечно писал бы одну и ту же ошибку в лог.
Такие письма пересылаются кнопкой из админки — после настройки SMTP.

### Защита от бесконечной досылки

Досылка **не правит** старую строку — она отправляет письмо заново и заводит
**новую** запись. Если бы старая осталась в статусе `failed`, она навсегда осталась
бы кандидатом: каждые 20 минут крон брал бы её снова, и покупатель получал бы одно и
то же письмо (в том числе с кодом сертификата) десятки раз.

Поэтому после **сделанной попытки** исходная запись снимается с очереди
(`markMailRetried`: `failed` → `skipped`, `error = superseded_by_resend`).
Статус `sent` в неё не пишется намеренно — это было бы неправдой: ушло *другое*
письмо, со своей строкой журнала.

Если попытки фактически не было (упало чтение журнала/БД — исключение в `resend`),
запись **сохраняет** место в очереди: транзиентная ошибка не должна навсегда лишать
покупателя письма с кодом.

## 7. Что нужно от владельца, чтобы включить почту

1. Завести/выбрать почтовый ящик магазина у провайдера (Яндекс 360, Mail.ru для
   бизнеса, Gmail Workspace, собственный релей).
2. Получить **пароль приложения** (не пароль от аккаунта) — у Яндекса/Gmail/Mail.ru
   обычный пароль по SMTP не работает.
3. Заполнить в `.env` сервера: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`,
   `SMTP_PASSWORD`, `MAIL_FROM`, `MAIL_FROM_NAME` (при 465 — ещё `SMTP_SECURE=true`).
4. Перезапустить приложение (`docker compose up -d app`).
5. Проверить в админке: раздел **«Письма»** должен показать зелёную плашку
   «Почта настроена: отправка с адреса …».
6. Желательно настроить **SPF/DKIM/DMARC** для домена отправителя — иначе письма с
   кодами сертификатов будут попадать в спам, что для денег на предъявителя
   равносильно неотправке.

До выполнения этих шагов магазин работает как прежде: заказы принимаются,
сертификаты выпускаются, письма отмечаются статусом «Пропущено».
